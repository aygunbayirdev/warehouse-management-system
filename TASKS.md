## Faz 8 — StockCount Modülü (Sayım + Düzeltme)
- [x] `StockCount` (Draft/InProgress/Completed), `StockCountLine` (SistemMiktarı satır girişinde Inventory'den okunup dondurulur, Fark = SayılanMiktar - SistemMiktarı), `StockCountAdjustment` (ayrı aggregate root, Pending/Approved/Rejected) entity'leri + migration (stockcount schema, snake_case)
- [x] Sayım oturumu açma (`CreateStockCountCommand`, Draft) / başlatma (`StartStockCountCommand`, InProgress — DepoSorumlusu/DepoMüdürü/Admin'e açık) / kapama (`CompleteStockCountCommand`, Completed); satır girişi (`SubmitStockCountLineCommand`, tüm rollere açık, aynı üründen ikinci satır engelleniyor); fark hesaplama satır girişi anında Inventory'nin `GetStockItemsQuery`'si ile yapılıyor
- [x] Sayım kapatıldığında farkı sıfır olmayan her satır için otomatik olarak Pending bir `StockCountAdjustment` oluşuyor (aynı transaction, aynı DbContext — modüller arası olmadığı için domain event'e gerek yok); düzeltme onay/red akışı (`ApproveStockCountAdjustmentCommand`/`RejectStockCountAdjustmentCommand`, DepoMüdürü/Admin'e açık) → onayda `StockCountAdjustmentApprovedDomainEvent` → Inventory'nin `IncreaseStockCommand`/`DecreaseStockCommand`'ından farkın işaretine göre doğru olanı çağıran handler (Faz 5/6/7'de kurulan modüller arası çağrı kalıbının beşinci uygulaması)
- [x] Uçtan uca doğrulandı: InProgress olmadan satır girişi reddi, duplicate ürün satırı reddi, sıfır fark → adjustment oluşturulmaması, pozitif ve negatif farkların doğru şekilde stok artış/azalışına yansıması, red edilen düzeltmenin stoku değiştirmemesi, satırsız sayımın kapatılamaması, geçersiz depo/401 koruması dahil
- [x] `WMS.Modules.StockCount` modül namespace'i ile aggregate root sınıfı `StockCount` aynı ada sahip olduğu için (`WMS.Modules.StockCount.Domain.StockCount`), `using WMS.Modules.StockCount.Domain;` + çıplak `StockCount` kullanımı C# derleyicisinde CS0118 ("ad alanı öğesi tür olarak kullanılıyor") hatası veriyor — çünkü isim çözümleme, `WMS.Modules` seviyesinde `StockCount` adlı bir alt ad alanını (modülün kendisini) tür aramasından önce buluyor. Çözüm: bu sınıfa referans veren her dosyada `using StockCountAggregate = WMS.Modules.StockCount.Domain.StockCount;` alias'ı kullanılıyor (bkz. `IStockCountWriteRepository`, `StockCountWriteRepository`, `StockCountDbContext`, `StockCountConfiguration`, `CreateStockCountCommandHandler`). Modül adı ile o modüldeki bir aggregate root'un adı birebir aynı olursa bu kalıp tekrar gerekir.

## Faz 16 — Transactional Outbox + Idempotency Guard (MVP sonrası, mimari derinleştirme)

CLAUDE.md, cross-module domain event akışını bilinçli bir MVP riskiyle belgeliyordu: event `SaveChangesAsync` sonrası **bellek içinde** dispatch ediliyordu, process commit ile dispatch arasında çökerse event sessizce kaybolabilirdi ("outbox/saga pattern kapsam dışı" notu). Portföy projesini gerçek hayata daha da yakınsatmak için bu kapatıldı — ayrıca bunun "sadece mesaj kaybını önleme" değil, "mesajın iki kez işlenmesini de önleme" gerektirdiği (inbox/idempotency) fark edildi ve ikisi birlikte uygulandı.

- [x] **Outbox yazımı**: `DomainEventDispatchInterceptor` (post-commit, bellek-içi MediatR publish) → `OutboxWritingInterceptor`'a dönüştürüldü (`WMS.BuildingBlocks.Infrastructure/Outbox/`): pre-commit `SavingChangesAsync` hook'unda domain event'leri, aggregate'in kendi değişikliğiyle **aynı transaction'da** `OutboxMessage` satırı (Id, Type=`AssemblyQualifiedName`, Payload=JSON, OccurredOnUtc, ProcessedAtUtc, Error, RetryCount) olarak yazıyor. Sadece event ÜRETEN 4 modül (Inbound/Outbound/Transfer/StockCount) kendi şemasında `outbox_messages` tablosuna sahip (`OutboxMessageConfiguration.cs`, her modülde aynı şablon) — Inventory/Catalog/Identity hiç event üretmediği için tablo almıyor, interceptor kayıtlı kalıyor ama zararsız (`entitiesWithEvents.Count == 0` kısa devresi).
- [x] **`OutboxProcessor<TDbContext>`** — kod tabanındaki ilk `BackgroundService`. Her üretici modülün kendi `Add{Module}Module`'unda `AddHostedService<OutboxProcessor<XxxDbContext>>()` ile register edildi (4 instance). 5sn polling, batch 20, `RetryCount < 10` (aşılırsa satır `ProcessedAtUtc IS NULL AND RetryCount >= 10` olarak kalıcı "manuel inceleme" işareti taşıyor, exponential backoff yok — bilinçli sınır, tek `backend` container'ı olduğu için leader election/distributed lock da yok). Aynı `typeof(DomainEventNotification<>).MakeGenericType(...)` + `Activator.CreateInstance` trick'iyle MediatR üzerinden dispatch ediyor — mevcut 5 domain event handler hiç değişmeden (sadece `SourceEventId`/`LineNumber` eklendi, aşağıya bkz) çalışmaya devam ediyor.
- [x] **Idempotency guard (Inventory)**: `DomainEventNotification<T>`'a `OutboxMessageId` eklendi. Yeni `Inventory.Domain.ProcessedDomainEvent` ledger'ı, composite key **`(SourceEventId, LineNumber)`** — sadece `SourceEventId` yetersizdi çünkü 4/5 event çok satırlı (`GoodsReceiptApproved` vb. → N ayrı stok komutu); `LineNumber` event içindeki 0-tabanlı satır sırası (StockCount'ta sabit 0). `IncreaseStockCommand`/`DecreaseStockCommand` bu iki alanı zorunlu parametre olarak alıyor, handler önce `ExistsAsync` kontrolü yapıp varsa no-op `Result.Success()` dönüyor, yoksa stok değişikliği + ledger satırı **aynı `SaveChangesAsync`'te** commit ediliyor (atomiklik buradan geliyor). Inventory tüm 5 akışın tek tüketicisi olduğu için tek bir ledger tablosu yeterli oldu.
- [x] **`DemoDataSeeder` + `Program.cs` düzeltmesi**: Seeder artık `app.Run()`'dan önce değil, `app.StartAsync()` sonrası çalışıyor — aksi halde `OutboxProcessor` hosted service'leri henüz başlamamışken seeder'ın "onayla → hemen stok oku" varsayımı GoodsReceipt onaylarından sonraki adımlarda `GoodsIssue.InsufficientStock` hatasıyla patlıyordu (gerçek bir regresyon, ilk test koşusunda bulundu). Ayrıca `DemoDataSeeder`'a `WaitForStockAsync` yardımcı fonksiyonu eklendi — Mal Kabul/Sevkiyat onayından sonra ilgili satırların Inventory'e (outbox relay üzerinden asenkron) yansımasını `GetStockItemsQuery` ile kısa aralıklarla polling yaparak bekliyor, sonraki adımlar (bir sonraki Sevkiyat, Sayım satır girişi) bu güncellemeye güvenle bağımlı olabiliyor.
- [x] 5 EF Core migration'ı eklendi (`AddOutboxMessages` × Inbound/Outbound/Transfer/StockCount, `AddProcessedDomainEvents` × Inventory) — `Program.cs`'in mevcut `MigrateAsync()` bloğu değişmeden otomatik uyguluyor.
- [x] Testler: mevcut `IncreaseStockCommandHandlerTests`/`DecreaseStockCommandHandlerTests`'e idempotency senaryosu eklendi; yeni `GoodsReceiptApprovedDomainEventHandlerTests` (çok satırlı event → sıralı `LineNumber`'lı komutlar); yeni entegrasyon testleri `OutboxMessageWrittenTransactionallyTests` (StockCount, outbox satırının aggregate ile aynı transaction'da yazıldığını kanıtlıyor) ve `ProcessedDomainEventIdempotencyTests` (Inventory, aynı `SourceEventId`+`LineNumber`'la iki kez gönderilen komutun stoğu sadece bir kez değiştirdiğini kanıtlıyor); mevcut `GoodsReceiptWorkflowTests` (functional) artık anlık değil **polling ile** stok kontrolü yapıyor — bu, gerçek `OutboxProcessor` `BackgroundService`'inin `WebApplicationFactory` içinde uçtan uca çalıştığı tek test. Toplam 40 backend testi, hepsi yeşil.
- [x] Doğrulama: izole taze bir Postgres container'ına karşı tüm uygulama gerçekten çalıştırıldı (demo seed dahil) — ilk denemede yukarıdaki `DemoDataSeeder` regresyonu bulundu ve düzeltildi, ikinci denemede sıfır hatayla tamamlandı; API üzerinden çekilen tüm stok miktarları elle hesaplanan beklenen değerlerle birebir eşleşti. Ayrıca canlı bir senaryo test edildi: bekleyen bir sayım düzeltmesi API üzerinden onaylandı, birkaç saniye içinde `OutboxProcessor`'ın bunu işleyip stoğu doğru düşürdüğü (42→40) doğrulandı.
- [x] `CLAUDE.md` güncellendi ("outbox/saga kapsam dışı" notu kaldırıldı, yerine gerçek mekanizma + idempotency guard + seeding'in asenkron akışa nasıl uyum sağladığı anlatıldı).

## Faz 20 — Güvenlik: Postgres'in İnternete Açık Olması

Hetzner'dan (Almanya BSI'nin bildirimini ileten) bir abuse maili geldi: sunucunun genel IP'sinde açıkça erişilebilir bir PostgreSQL sunucusu tespit edilmiş. `docker-compose.yml`'de `postgres` servisinin `ports: - "${POSTGRES_PORT:-5432}:5432"` satırı, Docker'ın varsayılan davranışı gereği portu **tüm arayüzlere** (`0.0.0.0`) yayınlıyordu — yani 5432 dünyaya açıktı.

- [x] **Kök neden**: Sunucudaki `ufw` durumu kontrol edildi, sadece SSH/80/443 izinliydi, 5432 açıkça izinli değildi — ama yine de erişilebiliyordu. Sebebi: **Docker, Linux'ta container port yayınlarken kendi iptables/NAT kurallarını ekliyor, bunlar ufw'nin filtrelerini tamamen atlıyor.** Yani "ufw kilitli" görünmesi yanıltıcıydı, Docker'ın kendi port yayını ufw'den bağımsız çalışıyordu.
- [x] **Düzeltme**: `docker-compose.yml`'de postgres portu `"127.0.0.1:${POSTGRES_PORT:-5432}:5432"` olarak değiştirildi — artık sadece sunucunun kendisinden (localhost) erişilebilir, dışarıdan tamamen kapalı. `backend` container'ı postgres'e Docker'ın iç ağı üzerinden (`Host=postgres`, servis adıyla) bağlandığı için bu değişiklik uygulamayı **hiç etkilemedi** — host port yayını, container-to-container iletişimini kullanmıyor.
- [x] Doğrulama: yerel ortamda `docker compose up -d postgres` ile yeniden oluşturulup `docker port wms-postgres`'in `127.0.0.1:5432` gösterdiği, backend'in (geçici bağlantı kopması dışında, kendiliğinden 5sn içinde toparlanarak) sorunsuz çalıştığı doğrulandı. Sunucuda `git pull && docker compose up -d postgres` ile deploy edildi — dışarıdan `91.99.75.164:5432`'ye bağlantı denemesi artık reddediliyor (`ufw`'ye ek kural gerekmeden, sorun kaynağında çözüldü), canlı `wms.aygunbayir.com` üzerinden gerçek giriş + `/api/warehouses` isteği sorunsuz çalıştı.
